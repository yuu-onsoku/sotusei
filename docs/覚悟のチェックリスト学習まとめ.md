# 覚悟のチェックリスト 学習まとめ

issue #118「覚悟のチェックリスト」を作ったときの記録。
猫を飼うときの「大変な現実」を一覧で見せ、すべてに納得したかを確かめる機能。
ブランチは `38checklist`。

---

## 0. どんな機能か

| | お迎え診断（#79） | 覚悟のチェックリスト（#118） |
|---|---|---|
| たとえ | 健康診断 | 絶叫マシンに乗る前の注意書き |
| 確かめること | 今、猫を飼える状態か | 大変さを知ったうえで、それでも飼うか |
| 入力 | ラジオボタンで1つ選ぶ | チェックボックスで ✅ を付ける |
| ログイン | 不要（入口の機能） | **必要**（ログイン後の機能） |

作りはお迎え診断と同じ形にした。

| 役割 | お迎え診断 | 覚悟のチェックリスト |
|---|---|---|
| 項目の一覧 | `config/diagnosis_questions.yml` | `config/checklist_items.yml` |
| 判定係 | `app/services/diagnosis_judge.rb` | `app/services/checklist_judge.rb` |
| テスト | `spec/services/diagnosis_judge_spec.rb` | `spec/services/checklist_judge_spec.rb` |

### 最初に決めたこと

- **ログイン必須にする。** 診断をクリアした人が次に進む、ログイン後の機能だから。
- **結果はデータベースに保存しない。** まずは診断と同じく session で動かす。保存は別の issue にする。
- **全部にチェックしなくても結果画面は出す。** 「16個中12個に納得」のように数を見せ、まだの項目を猫が教える。これが「覚悟の視覚化」になる。

### 進め方（5ステップ）

1. YAML にチェック項目を書く ✅
2. 判定クラス `ChecklistJudge` を作り、テストを書く ✅
3. ルーティングとコントローラーを作る
4. チェック画面と結果画面を作る
5. 診断結果画面からの導線をつなぐ

---

## 1. YAML で項目を管理する

### 1-1. なぜ YAML に分けるのか

YAML はお店の「メニュー表」。料理の作り方（コード）とは別の紙に書いておくので、項目を増やしたり文章を直したりするときにコードを触らなくて済む。

### 1-2. 書き方

```yaml
# 覚悟のチェックリスト
# 猫を飼うときの「大変な現実」の一覧
# text:     大変なこと（見出し）
# category: どの分類か（画面ではこの分類ごとにまとめて表示する）
# detail:   どれくらい大変かの説明

items:
  - text: "毎日、たくさん毛が抜けます"
    category: "毎日のお世話"
    detail: "特に春と秋は毛が生え変わる時期で、服やソファが毛だらけになります。毎日の掃除が必要です。"
```

| 書き方 | 意味 | たとえ |
|---|---|---|
| `items:` | 項目の入れ物の名前 | お道具箱 |
| `- ` | ここから新しい項目が1つ始まる | カード1枚 |
| `text:` / `category:` / `detail:` | 項目の中身 | カードの表・棚の名前・裏の説明 |

### 1-3. 気をつけること

- 字下げは**半角スペース**。`-` の前に2つ、`category:` と `detail:` の前に4つ（`text` の `t` と縦にそろえる）。
- 全角スペースやタブを使うと、読み込むときにエラーになる。
- 文章は `" "`（半角のダブルクォート）で囲む。
- `:` のあとに半角スペースを1つ入れる。
- 空行は入れてよい。分類の境目に空行を入れると、人間が読みやすくなる（読み込み結果は変わらない）。
- 一番上のコメントは取扱説明書。項目の種類（`category` など）を増やしたら、ここにも説明を足す。

### 1-4. 並び順が大事

- チェックボックスは、項目の**番号（0番、1番…）**で見分ける。
- 画面で分類ごとにまとめると、分類の並び順は **YAML で最初に出てきた順**になる。

だから、画面に出したい順に YAML の項目を並べておく。今回は、身近で軽い話から始めて、一番重い「15年の覚悟」で締める順にした。

1. 毎日のお世話（3項目）
2. ねこの行動（3項目）
3. 家や物への影響（4項目）
4. 健康とお金（3項目）
5. 暮らしと将来（3項目）

番号がずれるので、**並べ替えはコードを書く前**にやっておく。

### 1-5. 読み込めるか確かめる

```bash
docker compose exec web ruby -ryaml -e 'd=YAML.load_file("config/checklist_items.yml"); d["items"].each_with_index{|i,n| puts "#{n}: #{i["text"]}"}'
```

番号と見出しが、書いた項目の数だけ並べば成功。字下げを間違えると、エラーが出るか、表示される数が合わなくなる。

## 2. 項目の中身を考えるときのポイント

### 2-1. ほかの機能と重ならないようにする

最初は「住まいがペット可か確認が必要です」を入れていた。しかし、ペット可かどうかはお迎え診断の3問目でもう聞いている。チェックリストは診断をクリアした人が見るので、同じことを2回聞くことになる。

そこで、診断では聞いていない「退去時の修繕費」のほうに見出しを寄せて残した。

### 2-2. 言い方をそろえる

このリストは「大変な現実を知って、納得したら ✅」という仕組み。だから、項目は**事実を伝える形**（〜します、〜かかります）にそろえる。

- ✕ 「家族や来客に猫アレルギーの人がいないか確認しましょう」（やることリストの形）
- ○ 「猫アレルギーだと、一緒に暮らせないことがあります」（事実の形）

形がそろっていないと、何に ✅ を付けるのかがぶれる。

### 2-3. 多すぎるときは分類する

16項目が1列に並ぶと、途中で読むのに疲れてしまう。`category` を付けて棚に分けると、画面で見出しごとに表示できる。分類ごとの数をそろえる（今回は3〜4個）と、見た目もきれいになる。

## 3. 判定クラス ChecklistJudge

```ruby
# app/services/checklist_judge.rb
class ChecklistJudge
  # チェック項目（起動時に1度だけ読み込む）
  ITEMS = YAML.load_file(Rails.root.join("config/checklist_items.yml"))["items"].freeze

  def self.items
    ITEMS
  end

  # checked は ✅ が付いた項目の番号の配列
  # => ["0", "3", "5"]
  def initialize(checked)
    @checked = checked
  end

  # ✅ が付いていない項目を返す
  def unchecked_items
    self.class.items.reject.with_index do |_item, index|
      @checked.include?(index.to_s)
    end
  end

  # 全部で何項目あるか
  def total_count
    self.class.items.size
  end

  # ✅ が付いた項目の数（全体 − まだの数）
  def checked_count
    total_count - unchecked_items.size
  end

  # 全部に ✅ が付いたか
  def all_checked?
    unchecked_items.empty?
  end
end
```

### 3-1. 受け取るデータの形

画面のチェックボックスからは、✅ を付けた項目の**番号だけ**が配列で届く。

```ruby
["0", "3", "5"]   # 0番・3番・5番に ✅ が付いた
[]                # 1つも付けなかった
```

番号が文字列（`"0"`）なのは、画面から届く値はいつも文字列になるから。そのため、比べるときは `index.to_s` で数字を文字列に変える。

### 3-2. 各メソッドのたとえ

| メソッド | たとえ | 返すもの |
|---|---|---|
| `unchecked_items` | 名簿を上から見て、出席カードがある子を外す（`reject`）。残った子が欠席者 | ✅ のない項目 |
| `total_count` | クラスの人数を数える（`.size`） | `16` |
| `checked_count` | クラス全員から欠席者を引くと出席者の数になる | ✅ の数 |
| `all_checked?` | 欠席者リストが空っぽ（`.empty?`）なら全員そろった | `true` / `false` |

### 3-3. checked_count を「全体 − まだの数」で数える理由

`@checked.size`（届いた番号の数）で数えると、誰かがわざと存在しない番号 `"99"` を送ってきたときに、数をごまかされてしまう。

```ruby
ChecklistJudge.new(["0", "99"]).checked_count
# @checked.size で数えた場合    => 2（ごまかされる）
# 全体 − まだの数 で数えた場合  => 1（正しい）
```

`unchecked_items` は YAML の項目を基準に調べるので、YAML にない番号は最初から相手にしない。

### 3-4. その他の決まりごと

- `true` / `false` を返すメソッドの名前は、`?` で終える（`all_checked?`）。
- 定数 `ITEMS` はクラスが読み込まれたときに1度だけ作られる。`.freeze` を付けて、あとから書き換えられないようにする。
- `self.class.items` は「自分のクラスの `items`」という意味。インスタンスメソッドの中からクラスメソッドを呼ぶときに使う。

### 3-5. 手で動かして確かめる

```bash
docker compose exec web bin/rails runner 'j = ChecklistJudge.new(["0","3","5"]); puts j.checked_count'
```

実際に試した結果：

| 入力 | checked_count | all_checked? |
|---|---|---|
| `["0", "3", "5"]` | 3 | false |
| `[]` | 0 | false |
| `"0"` 〜 `"15"` の16個 | 16 | true |
| `["0", "99"]` | 1 | false |

## 4. テスト

`spec/services/checklist_judge_spec.rb` に9本書いた。

```
ChecklistJudge
  .items
    16項目読み込める
    すべての項目に見出し・分類・説明がある
  #checked_count
    1つもチェックしないと0になる
    3つチェックすると3になる
    存在しない番号は数に入らない
  #unchecked_items
    チェックしていない項目だけが残る
  #all_checked?
    全部チェックするとtrueになる
    1つもチェックしないとfalseになる
    1つでもチェック漏れがあるとfalseになる
```

### 4-1. 番号の配列を短く作る

```ruby
(0..15).map(&:to_s)   # "0" から "15" までの16個
(1..15).map(&:to_s)   # 0番だけ抜いた15個
(0..14).map(&:to_s)   # 15番だけ抜いた15個
```

0から15までの数字を1つずつ文字列に変えて配列にする。16個を手で並べなくて済む。

### 4-2. 境目を確かめる

`all_checked?` は「0個」だけでなく、「15個（あと1つ）」でも `false` になるかを確かめる。0個しか確かめないと、「1個でもチェックがあれば true」という間違ったプログラムでもテストが通ってしまう。

体重計の0kg合わせと同じで、**ぎりぎりの所**を確かめるのが大事。

### 4-3. 数だけでなく中身も確かめる

```ruby
expect(unchecked.size).to eq(1)
expect(unchecked.first["text"]).to eq(ChecklistJudge.items.first["text"])
```

残った数が1つかどうかだけでなく、「残ったのが本当に0番の項目か」も確かめる。

### 4-4. YAML の書き漏れもテストで見張る

```ruby
ChecklistJudge.items.each do |item|
  expect(item["text"]).to be_present
  expect(item["category"]).to be_present
  expect(item["detail"]).to be_present
end
```

あとで項目を増やしたときに `category` を書き忘れても、テストが教えてくれる。

## 6. 次にやること

### ステップ3：ルーティングとコントローラー

- お迎え診断と同じく `new`（チェック画面）・`create`（受け取って判定）・`result`（結果画面）を作る。
- ログイン必須にするため、コントローラーの一番上に `before_action :authenticate_user!` を書く（`questions_controller.rb` と同じ）。入口の受付係のようなもので、ログインしていない人をログイン画面へ案内する。
- リクエストspecでは `sign_in user` でログインさせる。「ログインしていないとログイン画面に飛ばされる」テストも書く。

### ステップ4：チェック画面と結果画面

- 見た目は診断画面をまねる。
- 項目は `category` ごとに見出しを付けて並べる。
- 結果画面では「16個中◯個に納得」と、まだの項目を表示する。

### ステップ5：診断結果画面からの導線

- ボタンは、ログインしていない人にも出してよい。Devise は「本当はどこへ行きたかったか」を覚えている。そのため、ボタンを押す → ログインする → チェックリストに自動で戻る、という流れになる。
